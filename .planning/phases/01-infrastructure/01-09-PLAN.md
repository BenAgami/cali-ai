<objective>
Deliver job progress to the client over Server-Sent Events (INFRA-03): `GET /api/sessions/:id/status`, Bearer-authenticated (D-05), emits the persisted state first then live events from the Redis progress bus (D-09, D-10), closes on a terminal state, and keeps percent monotonic on the wire (D-07).

Purpose: The phone shows stage label + percent while waiting (D-15) and learns when the result is ready (ROADMAP criterion 3).
Output: SSE stream helper, analysisStreamService (stream orchestration), thin controller + route, OpenAPI entry, unit tests (heartbeat/close/order/monotonic), real-HTTP integration test.

Design notes:
- Subscribe FIRST, then read the DB snapshot, then emit (RESEARCH Pitfall 5): events published between the two steps are not lost; a stale DB snapshot that is lower than an already-sent live event is dropped by the monotonic filter; a terminal live event closes the stream so the later DB write is ignored.
- No event history and no Last-Event-ID replay (D-09): a reconnecting client simply gets the current state again.
- No compression middleware exists; do not add one (it would buffer the stream). `X-Accel-Buffering: no` defeats proxy buffering; 15 s heartbeats beat typical 60 s idle timeouts.
- Three-tier split (CLAUDE.md): the controller only wires HTTP to the stream (`assertStreamable` -> `openSseStream` -> `attach`). The PENDING check, subscribe-then-read ordering, monotonic filter and terminal close live in `analysisStreamService`. The controller has no try/catch.
- Errors before headers are sent (404/409/401) are thrown by `assertStreamable` and go through the normal error handler. After headers are flushed the error handler cannot change a sent status, so `analysisStreamService.attach` catches, logs `{ err, sessionId }` and closes the sink. This single catch in the service is the documented post-flush exception.
</objective>

```typescript
export type AnalysisStreamSink = { send: (event: AnalysisStatusEvent) => void; close: () => void; onClose: (cb: () => void) => void };

class AnalysisStreamService {
  /** Throws before any stream is opened, so 404/409 go through the normal error handler. */
  async assertStreamable(userUuid: string, sessionId: number): Promise<void> {
    const session = await analysisStateService.findOwnedSession(userUuid, sessionId); // NotFoundError
    if (session.processingStatus === SessionStatus.PENDING) throw new ConflictError("No analysis has been started for this session");
  }

  /**
   * Pumps status events into an already-open sink. Never rejects: once headers are
   * flushed the HTTP error handler cannot change the response, so failures here are
   * logged and the sink is closed (the one documented post-flush catch, RESEARCH Pitfall 5).
   */
  async attach(sessionId: number, sink: AnalysisStreamSink): Promise<void> {
    let lastPercent = -1;
    const emit = (event: AnalysisStatusEvent): void => {
      const terminal = event.status === "COMPLETED" || event.status === "FAILED";
      if (!terminal && event.progress_percent < lastPercent) return; // D-07 monotonic on the wire
      lastPercent = Math.max(lastPercent, event.progress_percent);
      sink.send(event);
      if (terminal) sink.close();
    };
    try {
      const unsubscribe = await subscribeToAnalysisEvents(sessionId, emit); // subscribe FIRST
      sink.onClose(() => { unsubscribe().catch((error: unknown) => logger.warn({ err: toError(error), sessionId }, "Failed to unsubscribe analysis stream")); });
      const current = await analysisStateService.getStatusEvent(sessionId); // THEN read the snapshot (D-09)
      if (current) emit(current);
    } catch (error) {
      logger.error({ err: toError(error), sessionId }, "Failed to attach analysis status stream");
      sink.close();
    }
  }
}
export const analysisStreamService = new AnalysisStreamService();
```
Adapt the singleton/export style to whatever `analysisStateService.ts` uses (named default instance). Do not export `emit` or other internals — tests drive them through `attach` (CLAUDE.md).
