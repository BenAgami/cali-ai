<objective>
Close the loop from the phone (ROADMAP criterion 3 "the client receives SSE events"): add the native API layer for sessions (gzip capture upload per D-01, retry per D-16), a `useAnalysisStatus` hook using a fetch/XHR-based SSE client with a Bearer header (D-05), and a dev-only "Pipeline check" screen that runs create session -> submit synthetic capture -> watch stage label + percent (D-15) -> retry on failure, against the real API + worker. Then a human verifies it end-to-end on the Android dev build.

Discretion choice (D-05 client library): `react-native-sse` 1.2.x (XHR-based, custom headers, auto-reconnect). Note: D-05 says "fetch-based"; react-native-sse is XHR-based rather than fetch-based, but it meets D-05's actual intent (a client that can send the Bearer `Authorization` header, which the built-in EventSource cannot). Record this deviation in the SUMMARY. Chosen over `@microsoft/fetch-event-source` (depends on browser fetch streaming that RN lacks). Gzip on device: `fflate` 0.8.x (RN has no CompressionStream).

Scope: the real camera -> keypoints -> submit flow and the user-facing waiting UI are Phase 5 (FORM-02, FORM-03, FORM-08). This plan ships only the reusable API/hook layer plus a dev-only screen that proves the pipeline from a device. Both new deps are pure JS, so the 01-03 dev build is reused (no new EAS build).

Known pitfall: React Native Android auto-gzips STRING request bodies when the `Content-Encoding: gzip` header is set, which would double-compress. Sending the pre-gzipped bytes as a `Uint8Array` takes RN's binary path, which is not re-compressed. If the device upload returns 400 "invalid JSON"/inflate errors, this is the cause.
</objective>

export const useAnalysisStatus = (sessionId: number | null, runKey: string | null) => {
  const [event, setEvent] = useState<AnalysisStatusEvent | null>(null);
