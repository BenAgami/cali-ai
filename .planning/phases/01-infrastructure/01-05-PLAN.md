<objective>
Build the session state machine (INFRA-04) as ONE service, `analysisStateService`, that owns every `processingStatus` / `analysisStage` write: start a run with its capture, restart a failed run, advance stage, complete, fail, and reap stuck runs. All writes are guarded `updateMany` calls whose `where` names the expected prior state (and the current run's `bullmqJobId` for worker writes), so races and late writes are discarded instead of corrupting state. Every successful write publishes the derived status event over the progress bus.

Resolved open question (RESEARCH Q2): a session becomes PROCESSING at capture accept (not when the worker picks it up). `processingStartedAt` is set then, so the 3-minute reaper clock also covers a stalled queue. QUEUED is a persisted stage (`analysisStage = QUEUED`), not a `SessionStatus` value. This matches docs/architecture.md step 4 and D-17 (409 unless PENDING).

Purpose: The capture endpoint (01-07), worker + reaper (01-08) and SSE (01-09) all go through this service.
Output: analysisStateService with unit tests (exact Prisma call shapes) and real-DB integration tests (races, reaper, late writes).
</objective>

```typescript
import type { Logger } from "pino";
import { getPrismaClient, SessionStatus } from "@repo/db";
import type { AnalysisFailureReason, AnalysisStage } from "@repo/common";

export type CaptureInsert = {
  keypoints: Uint8Array;
  keypointsFormat: string;
  poseModelName: string;
  poseModelVersion: string;
  fps: number;
  frameCount: number;
  durationSec: number;
  cameraView: string | null;
  deviceModel: string | null;
  appVersion: string | null;
};
export type SessionSnapshot = AnalysisSnapshot & { bullmqJobId: string | null };
type WorkerStage = Extract<AnalysisStage, "ANALYZING_REPS" | "WRITING_FEEDBACK">;

const SNAPSHOT_SELECT = { id: true, processingStatus: true, analysisStage: true, analysisStageProgress: true, failureReason: true, bullmqJobId: true } as const;

export class AnalysisStateService {
  private get prisma() { return getPrismaClient(); }
  async findOwnedSession(userUuid: string, sessionId: number): Promise<SessionSnapshot>
  async startRunWithCapture(sessionId: number, capture: CaptureInsert, jobId: string): Promise<{ captureId: number }>
  async restartRun(sessionId: number, jobId: string): Promise<{ captureId: number }>
  async advanceStage(sessionId: number, jobId: string, stage: WorkerStage, subProgress?: number, log: Logger = logger): Promise<boolean>
  async completeRun(sessionId: number, jobId: string, log: Logger = logger): Promise<boolean>
  async failRun(sessionId: number, jobId: string, reason: AnalysisFailureReason, log: Logger = logger): Promise<boolean>
  async reapStuck(now: Date = new Date(), log: Logger = logger): Promise<number[]>
  async getCaptureForJob(sessionId: number, captureId: number): Promise<{ id: number; keypoints: Uint8Array | null; keypointsFormat: string } | null>
  async getStatusEvent(sessionId: number): Promise<AnalysisStatusEvent | null>
  private async publishSnapshot(sessionId: number, log: Logger): Promise<void>
}
export default new AnalysisStateService();
```
Implementation notes:
- Run-reset data shared by start/restart as a private helper `runResetData(jobId, now)` returning `{ processingStatus: SessionStatus.PROCESSING, analysisStage: "QUEUED", analysisStageProgress: null, processingStartedAt: now, processingFinishedAt: null, failureReason: null, bullmqJobId: jobId }`.
- In `startRunWithCapture` do the guarded `updateMany` BEFORE `poseCapture.create` inside one `$transaction(async (tx) => ...)`: Postgres row-locks the session on UPDATE, so a concurrent second submit waits, re-evaluates `processingStatus = PENDING`, gets count 0 and throws `ConflictError("Analysis already started for this session")`, rolling back cleanly. Map a P2002 from the create to the same ConflictError (defensive; use the constant from `utils/prismaErrorCodes.ts`).
- Cast `capture.keypoints` for Prisma's `Bytes` input if the generated type is `Uint8Array<ArrayBuffer>` (e.g. `new Uint8Array(capture.keypoints)`), without `any`.
- `publishSnapshot`: `findUnique({ where: { id }, select: SNAPSHOT_SELECT })`, `toStatusEvent`, then publish FIRE-AND-FORGET: `publishAnalysisEvent(event).catch((error: unknown) => log.warn({ err: toError(error), sessionId }, "Failed to publish analysis status event"))` — do NOT await the publish. ioredis (`maxRetriesPerRequest: null`) queues commands indefinitely while Redis is down, so an awaited publish would hang the capture request and every worker transition. ioredis still sends queued publishes in order, so event ordering is preserved. Wrap the snapshot read in try/catch with the same warn log. Publishing happens AFTER the transaction commits.
- `reapStuck` logs nothing itself except via `log` passed in; returns the ids actually failed (re-read snapshots, keep those with processingStatus FAILED and failureReason "TIMEOUT").
- No business logic outside this service writes `processingStatus` or `analysisStage` (later plans call these methods).
