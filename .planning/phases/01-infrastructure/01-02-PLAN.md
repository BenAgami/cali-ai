<objective>
Define the shared analysis-progress contract and the plumbing every other API plan builds on:
1. `@repo/common` status-event schema + stage list (D-06), and the single stage-to-percent table as a pure, unit-tested function in the API (D-07, D-08).
2. Analysis env config (attempts, backoff, LLM timeout, 3-minute stuck timeout, reaper interval) with a Zod refinement that enforces D-13 (stuck timeout > worst-case retry budget).
3. A Redis pub/sub progress bus (D-10) on a dedicated subscriber connection.

Purpose: The state machine (01-05), worker (01-08) and SSE endpoint (01-09) all depend on these contracts.
Output: analysis.ts in common, analysisProgress.ts util, env.analysis, progressBus.ts — each with unit tests.

Discretion choices made here (CONTEXT "Claude's Discretion"):
- Stages and ranges: QUEUED 0-10, ANALYZING_REPS 10-60, WRITING_FEEDBACK 60-95, COMPLETED 100. Contiguous ranges so percent never jumps backward between stages.
- Labels: QUEUED "queued", ANALYZING_REPS "analyzing reps", WRITING_FEEDBACK "writing feedback", COMPLETED "done". The label is a pure function of the persisted stage, so persisting the stage persists the label (D-06).
- Event field names `stage_label`, `progress_percent`, `failure_reason` are snake_case exactly as written in D-06 (locked), even though other API JSON is camelCase.
- Retry budget: attempts 3, exponential backoff base 2000 ms (waits 2 s, 4 s), LLM attempt timeout 40 s (D-12 said "about 45 s"; 40 s keeps a 39 s margin under 180 s), reaper every 30 s. Budget = attempts x llmTimeout + backoff x (2^(attempts-1) - 1) + 15 000 ms compute margin = 141 000 ms < 180 000 ms.
