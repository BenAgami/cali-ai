The two largest-risk items are structural: R-02 needs a new table because a per-user rolling count of retries cannot be derived from existing columns (a session can be retried many times and `PoseCapture` has one row per session, `session_id @unique`), and R-05/R-13/R-02 all want the same transaction to own the guard, the cap check and the write, so they must be designed together around `analysisStateService`.

Two environment facts shape the plan structure. Second, the integration project shares one Postgres (`:5433`, `app_test`) with `fileParallelism: false`, so integration runs from different plans must be serialized even when the plans' source files are disjoint.

The PR-fix commit audit found real defects, most overlapping findings: dead cap tests left after the per-exercise cap removal (`5683a54`), hard-coded `"metrics-v2"` in five test files (`82ad6b5`), a false comment in `keys.ts` (`6a2e2b3`), a third copy of the `URLSearchParams` boilerplate (`7e7f5a8`), duplicated API error-code string literals across API and native, new route-level Zod schemas hand-duplicated into the OpenAPI registry, and inline user-facing strings in two screens.

### Pattern 1: One transaction owns guard + cap + write (R-02, R-05, R-13)
**What:** `analysisStateService` already owns `startRunWithCapture` (guarded `updateMany` + create in one `$transaction`). Extend that pattern: lock the user row, count, throw `TooManyRequestsError`, then do the guarded write, all in the same `tx`. Publish the snapshot after commit (never inside the tx).
**When to use:** any state change that must be atomic with a quota or a result write.
**Example:**
```typescript
// apps/api/src/services/analysisStateService.ts (sketch; verify lock with the concurrency integration test)
const lockUser = async (tx: Prisma.TransactionClient, userId: number) => {
  await tx.$queryRaw`SELECT id FROM users WHERE id = ${userId} FOR UPDATE`;
};

async startRunWithCapture(
  sessionId: number,
  capture: CaptureInsert,
  jobId: string,
  cap: { userId: number; dailyCap: number },
): Promise<{ captureId: number }> {
  const captureId = await this.prisma.$transaction(async (tx) => {
    await lockUser(tx, cap.userId);                       // READ COMMITTED: the next statement sees committed rows
    const count = await tx.poseCapture.count({
      where: { session: { userId: cap.userId }, createdAt: { gte: new Date(Date.now() - DAY_MS) } },
    });
    if (count >= cap.dailyCap) throw new TooManyRequestsError(DAILY_MESSAGE, "DAILY_ANALYSIS_LIMIT_REACHED");
    /* existing guarded updateMany + create */
  });
  await this.publishSnapshot(sessionId, logger);
  return { captureId };
}

async restartRun(
  sessionId: number,
  jobId: string,
  cap: { userId: number; dailyRetryCap: number },
): Promise<{ captureId: number }> {
  /* stored capture lookup stays outside */
  await this.prisma.$transaction(async (tx) => {
    await lockUser(tx, cap.userId);
    const retries = await tx.analysisRetry.count({
      where: { session: { userId: cap.userId }, createdAt: { gte: new Date(Date.now() - DAY_MS) } },
    });
    if (retries >= cap.dailyRetryCap) throw new TooManyRequestsError(RETRY_MESSAGE, "DAILY_RETRY_LIMIT_REACHED");
    const { count } = await tx.workoutSession.updateMany({ where: { id: sessionId, processingStatus: SessionStatus.FAILED }, data: this.runResetData(jobId) });
    if (count === 0) throw new ConflictError("Only failed analyses can be retried"); // rolls back: refused retry is never recorded
    await tx.analysisRetry.create({ data: { sessionId } });
  });
  ...
}
```
Source: existing `startRunWithCapture` in `analysisStateService.ts:96-132` (pattern); Postgres `SELECT ... FOR UPDATE` semantics (MEDIUM, confirm by test).

### Pattern 2: Result write inside the completion transaction (R-05)
`analysisStateService.completeRunWithResult(sessionId, jobId, write: (tx) => Promise<void>, log): Promise<boolean>`: in one `$transaction`, do the guarded `updateMany` to COMPLETED first (row lock; `count === 0` returns false without calling `write`), then `await write(tx)`; publish after commit. `formAnalysisResultService.saveScored/saveUntrackable` become tx-accepting writers (`(tx, sessionId, metrics, outcome)`), and lose their own `isCurrentRun` check (the guard now lives in the caller's tx). Keeps three-tier: services call Prisma, worker orchestrates.

### Anti-Patterns to Avoid
- **Cap check outside the transaction** (current `assertUnderDailyCap`): the race in R-13.
- **Counting retries with a column on the session**: cannot express a rolling per-user window.
- **Publishing inside the tx**: `publishSnapshot` never throws/awaits Redis by design; keep it after commit.
- **Reading `phaseRef.current` for re-entrancy** (R-08): render-synchronized refs are stale within one tick.
- **Duplicating API error codes as string literals in native and API**: add shared constants to `@repo/common`.

### R-01 out-of-frame clamp: CONFIRMED (locked decision applies)
- **Evidence:** `apps/native/src/pose/useMediaPipePose.ts:25` `clamp01`; `:115-116` clamps x/y before `toUpright`; `:121` clamps visibility. ## Common Pitfalls

### Pitfall 1: Stale built packages
**What goes wrong:** API tests/type-checks run against old `@repo/common`/`@repo/db` `dist/`.
**Why:** both are consumed as built output (`packages/common/package.json` main `./dist`).
**How to avoid:** every plan that edits either package runs `yarn workspace @repo/common build` / `yarn workspace @repo/db db:generate && yarn workspace @repo/db build` before the gates. Parallel plans must not both rely on `dist/` they did not build; sequence plans that change `@repo/common` or the schema (see grouping).
**Warning signs:** TS errors for symbols that exist in `src`; Prisma `analysisRetry` missing from the client.

### Pitfall 2: Integration runs collide
**What goes wrong:** two plans running `test:integration` at once truncate each other's tables on `:5433`.
**How to avoid:** serialize integration runs across plans/waves (executor runs them one plan at a time even when source files are disjoint).

### Pitfall 3: A refused retry that still counts
**What goes wrong:** inserting the `AnalysisRetry` row before the guarded `updateMany` leaves a counted row when the update matches 0 rows.
**How to avoid:** insert last in the same `$transaction`; the 409/429 throw rolls everything back (integration test 3 in R-02).

### Pitfall 4: Publishing inside the transaction
**What goes wrong:** `publishSnapshot` reads via `this.prisma` (outside `tx`) and would publish a state that may roll back.
**How to avoid:** publish after the `$transaction` resolves (existing pattern in `startRunWithCapture`).

### Pitfall 5: R-06 resume loop
**What goes wrong:** auto-resuming an upload whenever prerequisites look met loops on a server 428 the client profile does not reflect.
**How to avoid:** await the profile refetch first, resume only if nothing is missing, otherwise surface a non-looping upload error.

### Pitfall 6: Migration timestamp ordering and checksum
**What goes wrong:** editing `20261112160346` changes its checksum; a new migration named earlier than `20261112160346` makes `migrate deploy` apply out of order on DBs that already ran it.
**How to avoid:** do not edit the kept migration; name the new one with a later timestamp.

### Pitfall 7: Prisma `$queryRaw` with `FOR UPDATE`
**What goes wrong:** assuming the lock works through the Prisma 7 driver adapter without proving it.
**How to avoid:** the concurrency integration test (R-13) is the proof; if it fails, fall back to `$executeRaw` with `pg_advisory_xact_lock(userId)`.

### Pitfall 8: Unit project must pass with Docker stopped
New unit tests must use `createPrismaMock()`; the mock needs `analysisRetry` and `$queryRaw` entries (add them to `tests/unit/helpers/prismaMock.ts`; the last commit range already touched it for another model).

## Open Questions

1. **Postgres `FOR UPDATE` through Prisma 7 `$queryRaw` (R-13/R-02).**
   - Known: READ COMMITTED gives per-statement snapshots, so lock-then-count is race-free in principle.
   - Unclear: behaviour under Prisma 7's driver adapter was not verified.
   - Recommendation: write the concurrency integration test first; fall back to `$executeRaw` with `pg_advisory_xact_lock(userId)` if the row lock misbehaves.
2. **`AbortSignal.timeout` in the API's Node version (R-18).** Engines not checked. Recommendation: confirm in `apps/api/package.json`/root `engines`; otherwise keep a local `AbortController` inside `feedbackService`.
3. **Scope of R-04 pagination.** It is the single largest item. If the user wants a smaller change, option C (unbounded when `workoutLogId` is given) plus documenting the bound is the fallback, but it leaves silent truncation for the all-runs list. Decide at plan time.
4. **R-14 contract widening.** Widening `status` changes a shared schema; confirm acceptable or ship only the `findUnique` change and record the status part as "won't fix, native ignores it".
5. **R-15 error code.** Doc-only vs adding `ANALYSIS_ALREADY_STARTED`. Recommendation: doc-only.
