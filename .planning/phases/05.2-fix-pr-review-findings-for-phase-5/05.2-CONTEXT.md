## Implementation Decisions

### Verification before fixing (locked)
- The review had no verification pass. Each finding must be confirmed against the current code before planning a fix.
- A finding that doesn't hold is recorded as dropped, with the reason, in the plan's SUMMARY, and no code changes for it.
- Each finding ID must still appear in some plan's `requirements`, either as fixed or as verified and dropped.

### R-01: out-of-frame detection (locked)
- Stop clamping landmark `x`/`y` in `apps/native/src/pose/useMediaPipePose.ts`. Keep clamping visibility, because `poseCapture.ts` bounds it to [0, 1].
- `toUpright` only rotates and mirrors, so out-of-range values stay outside the frame.
- `packages/common/src/validations/formSetup.ts` `clippedEdgeOf` already uses `<= EDGE_MIN` / `>= EDGE_MAX`. Update its comment, which says "the adapter clamps it". The "body partly out of frame" tests in `apps/api/tests/unit/.../formSetup.test.ts` must use past-edge values (`-0.1`, `1.1`).
- Add a trackability unit test: a push-up with wrists and ankles (joints 15, 16, 27, 28) at y = 1.05 and high visibility must yield OUT_OF_FRAME.

### R-02: retry cap (locked)
- **Setting:** new env var `FORM_ANALYSIS_DAILY_RETRY_CAP`, Zod `z.coerce.number().int().min(1).max(1000).default(5)`, exposed as `env.formAnalysis.dailyRetryCap`. Add it to `apps/api/.env.example` and `tests/unit/helpers/unitEnv.ts`. `tests/unit/config/env.test.ts` asserts the default.
- **Counting:** per user, over a rolling 24 h, across all sessions. Retries still don't count toward `FORM_ANALYSIS_DAILY_CAP`.
- **Over the cap:** 429 `DAILY_RETRY_LIMIT_REACHED`, message "You've reached today's limit for analysis retries. Try again tomorrow."
- **What counts:** only accepted retries. A refused retry (409, 428 or 429) doesn't count. Record the retry in the same transaction as the FAILED→PROCESSING restart.
- **Check order at retry:** consent (428), then the retry cap (429).
- **Docs:** the OpenAPI retry route lists the 429. `05-RUBRICS.md` section 11 and `.planning/STATE.md` describe the cap.
- **App:**
  - `useWorkoutRecordedSets.retrySet` must stop swallowing every error. On the retry-limit 429, the failed rows show the limit message instead of a Retry button.
  - `useRecordedSet`'s `submitOrRestart` path maps the same 429 to its own upload error, with no "Retry upload" button.

### X-01 and the status-code rule (locked)
- No hand-written HTTP status constants anywhere. Use `http-status-codes`.
- In `apps/native`, compare as `err.status === Number(StatusCodes.X)`: `ApiError.status` is a plain `number`, and `@typescript-eslint/no-unsafe-enum-comparison` rejects a bare enum comparison. This is the existing convention in `useLogin.ts` and `useWorkoutGenerate.ts`.
- Known sites: `hooks/useRecordedSet.ts` (`HTTP_CONFLICT`, `HTTP_PRECONDITION_REQUIRED`, `HTTP_TOO_MANY_REQUESTS`), `hooks/useAnalysisResultScreen.ts` (`CONFLICT_STATUS`), `hooks/queries/useSessionAnalysis.ts` (`CONFLICT_STATUS`). Grep the whole app for others.
